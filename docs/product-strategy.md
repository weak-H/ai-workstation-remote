# 产品战略共识：CI Repair Desk

> 版本：2026-10-20  
> 结论：用当前项目演进出一个运行在客户私有环境中的 CI 修复 Agent。首个产品卖“经过验证的修复结果”，统一控制面和跨 Agent 治理作为底层能力与长期平台方向。

## 1. 决策摘要

最有前景的首个产品不是手机远控器、通用多 Agent 控制台，也不是另一个云端编码 Agent，而是：

> **CI Repair Desk：当 PR 的构建或测试失败时，在客户自己的 Runner 中自动复现、诊断、生成最小修复、执行验证，并把带证据的修复 PR 交给工程师审批。**

首版聚焦 GitHub Actions 中可重复的 PR 检查失败，不直接处理生产部署、数据库变更或基础设施操作。

选择这个方向的原因：

1. CI 故障高频、损失可计算，客户能为缩短修复时间和减少值班负担付费。
2. 私有依赖、VPN、构建缓存和专用工具链让客户环境中的执行具有真实价值。
3. 当前仓库已有统一事件协议、Workstation Companion、Codex/Cursor/Claude Code adapter、任务时间线和审批界面，可复用为控制面与 Edge Runner。
4. 官方产品正在商品化手机远控、云任务和通用 Agent UI；仅做统一界面难以形成长期壁垒。
5. 从 CI 修复积累的任务结果、验证数据和环境模板，可以自然扩展为更广泛的 AgentOps 平台。

## 2. 三位产品经理 Agent 的角色与共识

本次评审由三个相互独立的产品经理 Agent 完成第一轮提案，再进行交叉质疑。

| Agent | 负责视角 | 第一轮主张 | 互评后的最终选择 |
|---|---|---|---|
| A：市场与用户需求 | 用户痛点、市场窗口、替代方案 | CI/发布失败修复 Agent | CI 修复结果产品 |
| B：产品与技术可行性 | 资产复用、MVP、依赖风险 | Local-first AgentOps 控制面 | CI 修复结果产品；控制面作为底座 |
| C：商业化与竞争反方 | 付费、获客、平台挤压、安全 | 跨 Agent 执行治理网关 | CI 修复结果产品；治理作为护栏和后续 SKU |

最终投票为 **3:0**：首个付费产品应卖“修复结果”，不应先卖抽象的治理能力。

争论后形成的关键共识：

- 统一任务、审批、审计是必要能力，但单独拿出来缺乏足够强的早期购买动机。
- 企业治理长期壁垒更强，但需要 SSO、RBAC、SIEM、策略防绕过和稳定公开接口，当前阶段销售与交付过重。
- CI 修复有明确触发器、验收标准和 ROI，适合作为进入客户环境的业务楔子。
- 产品必须坚持 BYOC、证据驱动和人工合并，避免退化成不可控的自动改代码工具。

## 3. 候选方向评估

评分为 1–5，越高越好；“交付难度”越高代表越难。

| 候选方向 | 付费动机 | 当前资产契合 | 抗平台挤压 | 交付难度 | 结论 |
|---|---:|---:|---:|---:|---|
| 个人多 Agent 手机遥控器 | 2 | 5 | 1 | 2 | 可作为开源获客入口，不作为主产品 |
| 通用多 Agent 任务台 | 3 | 4 | 2 | 3 | 是产品界面，不是独立价值主张 |
| 通用云端编码 Agent | 3 | 2 | 1 | 5 | 与大厂正面竞争，暂不进入 |
| 跨 Agent 执行治理网关 | 4 | 5 | 4 | 5 | 长期方向，早期采购周期过长 |
| 遗留系统迁移工厂 | 4 | 3 | 4 | 5 | 客单价高但容易变成咨询项目 |
| **BYOC CI 修复 Agent** | **5** | **4** | **4** | **3** | **首个产品** |

## 4. 目标用户与使用边界

### 最小理想客户画像

- 20–100 名工程师的 B2B 软件团队。
- 使用 GitHub 和 GitHub Actions；后续再支持 GitLab CI。
- 每周至少出现 5–10 次可重复的构建、类型检查或测试失败。
- 存在私有包、VPN、内部服务、自托管 Runner 或专用构建环境。
- 团队已经使用 Codex、Claude Code、Cursor 中的一种或多种工具。
- 购买者是 VP Engineering、研发负责人或平台工程负责人。
- 日常用户是值班工程师、Tech Lead 和 PR 作者。

### MVP 支持的失败类型

- 单元测试或集成测试失败。
- TypeScript 类型检查、lint 和构建失败。
- 依赖升级导致的确定性兼容问题。
- 能在目标 Commit 上稳定复现的缺陷。

### MVP 明确不处理

- 自动合并 PR。
- 自动部署生产环境。
- 生产数据库和基础设施变更。
- 不可重复、需要长期线上观测的偶发故障。
- 通用远程桌面或完整手机 Shell。

## 5. 核心工作流

```text
GitHub Actions PR 检查失败
            |
            v
控制面创建修复任务并选择客户 Runner
            |
            v
Runner 检出失败 Commit，复现原始错误
            |
            v
Codex 诊断根因并生成最小补丁
            |
            v
重跑失败项、相关测试和必要静态检查
            |
            v
生成证据包：根因、命令、diff、测试结果、风险
            |
            v
手机 / Web / Slack 人工审批
            |
            v
创建修复 PR；CI 再次验证
```

任何阶段无法复现、证据不足、预算超限或触发高风险策略时，任务停止自动执行并携带完整上下文转交人工。

## 6. 产品承诺

### 一句话定位

> 让 PR 的 CI 故障在真实私有环境中自动完成复现、修复和验证，工程师只审核有证据的结果。

### 用户真正购买的结果

- 更短的 CI 恢复时间。
- 更少的重复排障和值班中断。
- 一个已经复现原错误并通过相关测试的最小修复 PR。
- 清晰、可追踪的命令、代码变更和审批记录。

### 不是核心卖点的能力

- “支持很多模型”。
- “有手机端”。
- “可以聊天”。
- “可以云端运行 Agent”。
- “一个页面看到所有任务”。

这些能力可以帮助交付，但不能单独构成购买理由。

## 7. 差异化与长期壁垒

### 初期差异化

1. **真实客户环境执行**：利用私有依赖、VPN、缓存、证书和内部工具链。
2. **证据驱动**：必须先复现失败，再提交补丁，并展示验证范围与未解决风险。
3. **人保持控制权**：首版只创建待审 PR，不自动合并或部署。
4. **Agent 可替换**：先用 Codex，协议允许后续加入 Claude Code、Cursor 或其他 runtime。
5. **云端最小知情**：Runner 执行代码和命令；控制面保存必要任务元数据和经策略允许的证据。

### 可积累的长期壁垒

- 不同失败类型对应 Agent、模型、提示和环境的成功率数据。
- 从失败日志到最终 CI 结果的完整结构化轨迹。
- 自动回退、转人工和恢复机制。
- 企业内部环境的 Runner 模板和连接器。
- 风险分类、审批策略和可验证的执行证据链。
- 跨 Agent 的兼容测试与稳定事件语义。

## 8. 与当前项目的衔接

### 可以直接复用

- `packages/protocol`：任务状态、控制权、能力、审批、历史、产物、事件序列和命令模型。
- `apps/mac-companion`：演进为 Edge Runner 和本地最终策略边界。
- Codex adapter：作为首个执行 runtime。
- Cursor adapter：早期保留为实验性的观察和消息能力，不纳入核心 SLA。
- `apps/mobile`：演进为异常、审批和结果收件箱。
- `services/control-plane`：演进为账号、任务、设备和加密信封协调服务。

### 必须补齐

- 持久事件账本、游标回放和跨重启命令幂等。
- 安装级设备身份，移除硬编码 `deviceId`。
- QR 挑战、设备密钥、签名命令和端到端加密信封。
- `create_task`、仓库、Commit、PR、Runner、验证证据和成本实体。
- Linux Runner，以及可重复的容器化任务环境。
- GitHub App、Checks/Webhook 和 PR 写入能力。
- Agent 版本探测、健康检查、错误分类和契约测试。
- 多个并行审批及明确的命令最终执行结果。

## 9. 推荐架构

```text
                       +----------------------+
GitHub / CI Webhook -->| Cloud Control Plane  |
                       | identity / task DB   |
Mobile / Web / Slack ->| policy / notification|
                       +----------+-----------+
                                  |
                       outbound encrypted link
                                  |
                +-----------------+-----------------+
                |                                   |
        Customer Mac Runner                 Customer Linux Runner
        local workspace                     CI-like workspace
                |                                   |
        Codex / other adapter               Codex / other adapter
                |                                   |
        tools, VPN, secrets                 tests, build, git
```

控制面负责任务和协作，Runner 负责代码与工具执行，Agent runtime 负责推理和工具循环。三层必须保持独立，以便未来替换 Agent 或增加托管沙箱。

Codex 可通过开源 App Server 或 SDK 集成。生产版 Runner 应优先使用 `stdio` 管理本地 App Server，再由 Runner 使用自有稳定协议连接控制面；不要把仍属实验性质的 App Server WebSocket transport 直接暴露为产品边界。

## 10. 8–12 周 MVP

### 第 0 阶段：先验证问题，1–2 周

- 访谈 15 个研发负责人或平台工程负责人。
- 收集至少 100 个已脱敏的历史 CI 失败样本。
- 记录人工定位时间、修复时间、失败类型和环境依赖。
- 招募 3–5 家愿意提供真实失败样本的设计伙伴。

### 第 1 阶段：可靠 Runner，2–3 周

- 增加 SQLite 事件账本、游标回放和命令幂等。
- 生成并安全保存唯一 Runner 身份。
- 增加任务创建、仓库、Commit 和验证证据协议。
- 将 Codex adapter 抽象为可由 Mac/Linux Runner 执行的 runtime。

### 第 2 阶段：CI 修复闭环，3–4 周

- 接入 GitHub App 和 GitHub Actions 失败事件。
- 在客户 Runner 中检出 Commit 并复现失败。
- 让 Codex 生成最小补丁并重跑目标测试。
- 生成证据包并创建修复分支或草稿 PR。
- 明确失败转人工和预算终止机制。

### 第 3 阶段：审批与试点，2–3 周

- Web、手机和 Slack 审批通知。
- 任务时间线、diff、测试结果和风险说明。
- 试点团队、项目归属和基础审批人配置。
- 记录修复接受率、耗时、成本和人工介入原因。

### 延后到验证成功之后

- Claude Code 第二 runtime。
- 自动选择最佳 Agent 或模型。
- 自营大规模云沙箱。
- 企业 SSO、SCIM、SIEM 和复杂 RBAC。
- 原生 iOS 客户端。
- 自动合并和生产发布。

## 11. 必须验证的假设

| 假设 | 通过标准 | 验证方法 |
|---|---|---|
| CI 故障足够痛 | 目标团队每月至少浪费 20 个工程师小时 | 访谈并复盘最近 30 天失败记录 |
| Agent 能产生有效修复 | 限定失败集中至少 30% 生成被接受的修复 PR | 100 个历史失败离线回放 |
| 产品优于建议机器人 | 用户愿为验证通过的 PR 付费，而不仅是错误解释 | 设计伙伴付费试点 |
| BYOC 安装可接受 | 从安装到首个任务少于 30 分钟 | 观察式安装测试 |
| 私有环境形成差异 | 至少 30% 样本不能在普通公共云环境稳定复现 | 对样本标记环境依赖 |
| 付费成立 | 5 家设计伙伴中至少 3 家愿付费，2 家承诺月费 1,000 美元以上 | 带明确价格的试点或 LOI |

跨 Agent 路由不是 MVP 成立的前提。只有在同一任务集上相较固定 Agent 提升至少 15% 成功率或降低至少 20% 成本后，才把它升级为主卖点。

## 12. 北极星指标与护栏指标

### 北极星指标

**每周被工程师接受并最终通过 CI 的自动修复 PR 数量。**

### 核心指标

- 修复 PR 接受率。
- 首次修复后 CI 通过率。
- 从失败到草稿 PR 的中位时间。
- 每个成功修复节省的人工小时。
- 每个成功修复的模型与计算成本。
- 需要人工介入的原因分布。

### 安全与质量护栏

- 未先复现原错误却提交补丁的任务数必须为 0。
- 未经授权执行高风险动作的次数必须为 0。
- 重复执行已确认命令的次数必须为 0。
- 自动合并和自动生产部署在 MVP 中必须为 0。
- 每个任务必须保留明确的最终状态和验证证据。

## 13. 商业模式与获客

### 初期收费方式

设计伙伴阶段优先采用固定月费，而不是复杂 token 计费：

- 每团队每月 500–2,000 美元，限制仓库、并发任务和任务预算。
- 客户自带模型/API 授权，产品不共享或转售个人订阅额度。
- Runner 使用客户已有 Mac、服务器或自托管 CI 资源。

确认稳定价值后，可拆分为平台费、活跃开发者席位和可选托管 Runner 计算费。

### 获客路径

1. 通过开源 Companion/Runner 和个人任务收件箱吸引开发者。
2. 发布真实 CI 失败基准、修复率和环境复现报告。
3. 从已经有私有 Runner、复杂 monorepo 或内部依赖的团队寻找设计伙伴。
4. 用“减少 CI 故障处理时间”进入研发预算，而不是先进入安全或合规预算。
5. 任务量形成后，再向平台工程和安全团队销售统一策略与审计升级包。

## 14. 风险与应对

### 平台厂商快速进入

GitHub、OpenAI、Cursor 和 Anthropic 都可能继续补齐“失败到 PR”的能力。应避免依赖通用 Agent UI，持续强化私有环境复现、证据质量、跨 Agent 回退和企业内部连接器。

### Adapter 不稳定

优先使用公开 SDK、CLI 结构化输出或 App Server。内部数据库读取和辅助功能路径只能是实验性兼容层，不能进入企业核心 SLA。

### 安全责任

默认最小权限、任务级凭据、网络策略、预算与超时；高风险操作拒绝或要求审批。准确表达隐私边界：代码与工具执行留在客户环境，不代表发送给模型供应商的必要上下文也留在本地。

### 结果质量不稳定

用失败样本基准、独立验证步骤和证据门槛约束 Agent。修复无法验证时必须转人工，不能为了成功率伪造完成状态。

### 定制服务失控

只支持标准 GitHub、Runner 镜像、环境变量和脚本接口。客户特有流程通过配置或插件接入，不为每个客户长期维护分叉版本。

### 单位经济性

设置任务 token、时间、重试和并发预算。早期让客户自带模型授权，不承担不可预测的推理成本。

## 15. 止损线

完成 12 周验证后，出现以下任意两项，应停止商业化投入或退回开源个人工具：

- 5 家设计伙伴中少于 2 家愿意付费。
- 限定任务集的可接受修复率低于 20%。
- 多数目标故障可被现有公共云 Agent 稳定解决，BYOC 没有实际优势。
- 安装和接入持续超过 1 小时，需要大量人工服务。
- 用户主要使用手机查看状态，很少消费自动修复结果。
- Adapter 维护成本高于新增客户带来的收入。

## 16. 后续平台演进

```text
阶段 1：PR CI 修复
    -> 阶段 2：Issue 修复、依赖升级、发布前验证
    -> 阶段 3：多 Agent 路由、失败自动回退、团队策略
    -> 阶段 4：企业 AgentOps 治理网关
    -> 阶段 5：本地、BYOC 与托管云 Runner 混合调度
```

CI Repair Desk 是获客楔子；长期产品是 vendor-neutral、local-first 的 Agent 执行与治理平台。顺序不能倒过来：先证明能持续交付客户愿意付费的工程结果，再把底层控制能力平台化。
